# V6 deployment and data handling
- Public demo: HTTPS hostname only, RSVP requires a high-entropy invitation code when WEDDING_PUBLIC_ORIGIN is configured. The code is stored in data/invite-code.txt, outside Git; share with verified guests only. Admin token is separate. Origin and invite checks, honeypot, bounded request size, global and per-name budgets reduce abuse; these are not a full WAF. No guest information is sent by GitHub Pages.
- Admin UI: loopback /admin/; token is held only in JS memory. Search, filter, totals, export and delete are supported. Do not expose /admin/ or /api/wedding/admin/* through public tunnel. Deletion does not immediately purge previous backups.
- Backup: run backup-wedding.ps1 daily with protected DataDir and node path. SQLite online backup, integrity_check, 30-day backup retention by default. This retention is an operational default, not an agreed retention policy for live guest records; confirm retention and consent before real use. Restore rehearsal: node backup-wedding.cjs restore-check <backup> <new-absolute-path>. Never overwrite an active DB. For actual restore stop the wedding task only, make a fresh recovery backup, validate replacement offline and retain the previous data/WAL for rollback. Do not restore production without operator approval.
- Keep V5 release and task disabled as rollback. Use verified main SHA only; restart only wedding service, do not restart any existing shared tunnel.
- QA: node tools/test-wedding-v6.cjs; node tools/test-wedding-v5.cjs; node tools/test-wedding-server-browser.cjs; node tools/test-wedding-v4.cjs.
- Date and venue in original site are demo data; confirm before opening real RSVP.
